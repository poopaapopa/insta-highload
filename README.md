## 3. **Глобальная балансировка**

#### 3.1 Домены

Instagram разделяет трафик на динамический (API) и статический (CDN) для оптимизации.

*   **Основной домен:** `i.instagram.com` (мобильный API), `www.instagram.com` (Web).
*   **CDN домены (Media):** `scontent.cdninstagram.com` (Фото/Видео). Используется Domain Sharding для обхода лимитов браузеров и гео-распределения.
*   **Graph API:** `graph.instagram.com` (Для сторонних разработчиков и бизнес-интеграций).

#### 3.2 Data Centers
Instagram — глобальный сервис с аудиторией 2+ млрд человек. В отличие от локальных сервисов, он требует размещения Origin-датацентров (где хранятся данные) на разных континентах.
Мы используем инфраструктуру Meta.

#### 3.3 Технологии глобальной балансировки

**DNS (Cartographer)**

Используем **Geo-DNS** ([**Cartographer** Meta](https://engineering.fb.com/2017/08/21/networking-traffic/steering-oceans-of-content-to-the-world/)) для направления пользователя на ближайший Edge Hub, а затем **Backbone Routing** для доставки запроса в Origin DC.

1.  Пользователь из Индии открывает приложение.
2.  Cartographer определяет, что пользователь находится в подсети определённого провайдера.
3.  Система знает, что сейчас маршрут до **Сингапура** перегружен, и направляет пользователя на Edge-ноду в **Мумбаи** (кэширующий прокси), которая по оптике соединена с Сингапуром.
4.  DNS возвращает IP ближайшей Edge-ноды.

При этом Edge отдает статику из локального кэша, а запрос API летит по внутренней оптике Meta в **Oregon DC (USA West)**.

**BGP Anycast**

Для обеспечения минимальной задержки и защиты от DDoS используем технологию **IP Anycast**.

Единый диапазон IP-адресов (например, для DNS-серверов и CDN-фронтов) анонсируется одновременно из всех PoP (точек присутствия) по протоколу BGP. → Глобальная сеть интернет автоматически направляет запрос пользователя к топологически ближайшему дата-центру (ользователь из Берлина → маршрутизируется в узел **Frankfurt Edge**.). В случае аварии в узле (например, Франкфурт недоступен), BGP-маршруты автоматически перестраиваются, и трафик из Берлина направляется в следующий ближайший узел (например, Амстердам) без необходимости изменения DNS-записей.

## 4. **Локальная балансировка**

Для локальной балансировки (по приходе в конкретный ДЦ) применим **двухуровневую архитектуру балансировки (L4 + L7)**, которая в связке с оркестратором **Kubernetes** обеспечит автомасштабирование и отказоустойчивость.

### 4.1 Layer 4 Load Balancing

На транспортном уровне при входе в ДЦ пакеты встречает L4-балансировщик. В масштабах Instagram классические прокси (вроде Nginx stream) не справляются с объемом пакетов, поэтому Meta использует программный балансировщик на базе eBPF/XDP (eXpress Data Path) - **Katran**.

Его ключевое преимущество заключается в том, что он работает на высокой скорости, перехватывая и перенаправляя сетевые пакеты на уровне драйвера сетевой карты, еще до того, как операционная система выделит под них память. Это позволяет Meta не использовать отдельные серверы под балансировку: Katran может работать фоном на любом сервере в ДЦ параллельно с другими задачами.

Katran использует технологию инкапсуляции IP-in-IP при пересылке пакетов внутри ДЦ для реализации подхода Direct Server Return (DSR). Балансировщик принимает входящий HTTP-запрос от клиента и пересылает его на нужный L7-прокси. Когда L7 формирует объёмные данные, этот ответ отправляется напрямую пользователю в обход балансировщика L4. Katran же позволяет этому случится, недавая IP адресу измениться при пересылке на L7 путём создания обёрточного пакета над существующим. Такая асимметричная маршрутизация полностью исключает Katran из пути исходящего трафика, гарантируя отсутствие перегрузок на входе.

*Источник*: [Open-sourcing Katran, a scalable network load balancer](https://engineering.fb.com/2018/05/22/open-source/open-sourcing-katran-a-scalable-network-load-balancer/).

### 4.2 Layer 7 Load Balancing

После прохождения транспортного L4 трафик попадает на уровень L7-прокси. Здесь также в отличие от многих компаний, использующих Nginx или Envoy, Meta использует собственную разработку под названием **Proxygen**. Это высокопроизводительный HTTP-фреймворк, написанный на C++. Изначально проект создавался именно как кастомный обратный прокси-сервер (отсюда и название), так как существующие на рынке решения не масштабировались под нужды компании и не обладали необходимой гибкостью для внедрения специфических функций, таких как проприетарные алгоритмы балансировки (с учётом загрузки ЦП и локализации данных) или ранняя поддержка WebSockets и TLS false start (ещё до появления QUIC).

Proxygen выделяется своей архитектурой: обработка разделена на сессии, кодеки, транзакции и обработчики. Это позволило фреймворку адаптировать новый протоколы HTTP/3 без необходимости дублирования или переписывания базового сетевого кода. Внутри Proxygen использует неблокирующий ввод-вывод и механизм Linux epoll, что делает сервер эффективнее по процессору и памяти. Также активное использование семантики перемещения из современного C++ позволяет передавать объёмные данные, характерные для медиаконтента Instagram, без лишнего копирования объектов в оперативной памяти и риска утечек.

Что же происходит на L7 уровне? Во-первых, это TLS Termination: Proxygen расшифровывает входящий безопасный трафик, снимая эту вычислительную нагрузку с серверов с бизнес-логикой (после чего общение внутри дата-центра идет уже по легкому внутреннему протоколу Thrift). Во-вторых, как уже говорилось выше, архитектурная гибкость Proxygen позволила Instagram одним из первых в мире внедрить QUIC, который снизил задержки при нестабильном интернете, избавив пользователей от блокировки начала очереди при потере пакетов. В-третьих, здесь происходит фильтрация: система интегрирована с внутренним мониторингом ODS, что позволяет нивелировать DDoS-атаки на границе сети.

*Источники*: [Introducing Proxygen, Facebook's C++ HTTP framework](https://engineering.fb.com/2014/11/05/production-engineering/introducing-proxygen-facebook-s-c-http-framework/), [How Facebook is bringing QUIC to billions](https://engineering.fb.com/2020/10/21/networking-traffic/how-facebook-is-bringing-quic-to-billions/).

### 4.3 Оркестрация

Вся бизнес-логика Instagram также, как и в большинстве компаний, упакована в контейнеры. Однако как и в других областях, вместо повсеместно использумого решения, Meta использует собственную систему управления кластерами под названием **Twine**. Он рассчитан на куда больший масштаб чем Kubernetes - Twine оркестрирует все дата-центры Meta по всему миру. Преимущество Twine заключается в распределении задач с учетом энергопотребления серверов, износа оборудования и суточных колебаний трафика.

Также система оркестрации тесно связана с балансировщиками L7 через механизм Health Checks. Twine постоянно мониторит состояние каждого контейнера. Если сервер физически выходит из строя или процесс зависает, оркестратор немедленно исключает его IP-адрес из таблиц маршрутизации Proxygen и перераспределяет входящие запросы на рабочие машины. Одновременно с этим Twine поднимает новые копии упавшего сервиса на свободных серверах. Это гарантирует отказоустойчивость сервиса как во время пиковых нагрузок, так и при выходе из строя немалого количества оборудования.

*Источник*: [Twine: A unified cluster management system](https://engineering.fb.com/2019/06/06/data-center-engineering/twine/).

### Обоснование выбора СУБД

| СУБД | Связанные таблицы | Обоснование выбора (Архитектурное решение) |
| :--- | :--- | :--- |
| **PostgreSQL** | `users`, `posts`, `stories`, `comments`, `media`, `follows`, `chats`, `chat_participants` | **Ядро и транзакции.**<br>Эти таблицы требуют строгой консистентности (ACID-транзакций) и сохранения реляционных связей (кто автор, кому ответили). Несмотря на большой объем, эта нагрузка отлично масштабируется путем горизонтального шардирования кластера (например, разделение по хэшу `user_id` на 100+ физических серверов). |
| **Cassandra** | `messages`, `post_likes`, `comment_likes` | **Сверхбыстрая запись.**<br>Как показали расчеты выше, эти три таблицы генерируют более 80% всего объема данных и данные в основном только добавляются. Реляционная БД не справится от постоянных обновлений огромных B-Tree индексов. Cassandra, благодаря структуре LSM-Tree и партиционированию (по `chat_id` или `post_id`), позволяет писать данные на диск последовательно и без блокировок. |
| **Redis** | `sessions`, `user_stats`, `post_stats`, `comment_stats` | **Кэширование, сессии и атомарные счетчики.**<br>1. Валидация токена в сессиях (`access_token`) происходит при каждом API-запросе. Чтение с диска дало бы огромную задержку. Redis отдает данные из оперативной памяти и автоматически удаляет TTL токены.<br>2. Лайки в счётчиках ставятся со скоростью десятки тысяч RPS. Обновление счетчика напрямую в PostgreSQL вызовет блокировки. В Redis операция `INCR` атомарна и мгновенна, а данные периодически передаются в основную БД фоном. |
| **Elasticsearch** | `search_user_index`, `search_post_index` | **Полнотекстовый поиск и ранжирование.**<br>Классические SQL-базы не умеют эффективно искать по словам (особенно с опечатками) на крупном масштабе. ### Репликация
Обеспечить отказоустойчивость и разгрузить основные сервера от тяжелых запросов на чтение (формирование ленты, просмотр профилей).

Мы используем архитектуру **Master-Replica**:
*   **Master-узел:** Принимает 100% запросов на запись (регистрация пользователя, создание нового поста, подписка). Мастер всегда один на каждый кластер/шард, чтобы избежать конфликтов.
*   **Read Replicas:** 3-5 серверов, которые асинхронно копируют данные с Мастера. Они принимают 100% запросов на чтение. 

**Кросс-региональная репликация:**
Так как пользователи Instagram распределены по всему миру, применяется географическая репликация.
Мастер-база `users` физически находится в США. Пользователь из Индии подписывается на блогера запрос на запись летит по оптике в США. Это занимает ~150 мс. Затем база в США асинхронно реплицирует эти изменения на Read-реплику в Сингапуре. Когда другой пользователь из Индии открывает список подписок этого блогера, запрос на чтение (`SELECT`) идет в локальную реплику в Сингапуре. Мы жертвуем строгой консистентностью в пользу скорости.

### Партиционирование
Разбить одну гигантскую таблицу на более мелкие физические части **внутри одного сервера**, чтобы ускорить работу индексов и упростить удаление старых данных. Это применяется для таблиц, которые имеют ярко выраженную привязку ко времени.

*   **Таблица `stories`:**
    В ней лежат сотни миллиардов записей, но большинство запросов обращаются только к активным историям. Мы партиционируем таблицу по полю `is_archived`. Активная партиция лежит на сверхбыстрых NVMe-дисках и закэширована в ОЗУ. Старые партиции переносятся на более медленные и дешевые SSD-диски.
*   **Таблица `dwh_events`:**
    Таблица партиционируется по месяцам (`YYYY-MM`). Когда логам исполняется, допустим, 3 года и их нужно удалить, мы не делаем тяжелую команду `DELETE FROM dwh_events WHERE date < ...`, а просто выполняем `DROP PARTITION 2023-01`.

### Шардирование
Разделить большую таблицу (например, `posts`) на несколько разных физических серверов, так как она не помещается ни на один жесткий диск.

Мы применяем алгоритм логического шардирования, который используется в самом Instagram.

**1. Выбор Ключа Шардирования**
Для таблиц `users`, `posts`, `stories`, `follows` ключом шардирования выступает **`user_id`**. 90% запросов в Instagram связаны с конкретным профилем. Когда мы открываем страницу пользователя, нам нужны его данные профиля и его посты. Если шардировать по `user_id`, и профиль, и все посты этого человека физически окажутся на **одном и том же сервере**. Базе данных не нужно делать кросс-серверные JOIN-запросы по сети, что работает в сотни раз быстрее.

**2. Логические Шарды**
Вместо того чтобы жестко привязывать пользователей к 10 физическим серверам, создадим 10 000 логических шардов. Допустим хэш-функция: `shard_id = user_id % 10000`. Тогда у нас есть таблица маршрутизации, которая определяет, что логические шарды от 1 до 1000 лежат на физическом сервере `DB-Node-1` (к примеру).

**3. Шардирование NoSQL (Cassandra)**
Для таблиц `messages` и `post_likes` шардирование встроено в архитектуру самой базы. Ключом партиционирования выступает `chat_id` (для сообщений) и `post_id` (для лайков). С помощью алгоритма консистентного хэширования Cassandra сама распределяет чаты по серверам. При добавлении новых нод в кластер данные автоматически перебалансируются.

## 7. **Распределённые алгоритмы**

В высоконагруженной архитектуре Instagram классические подходы к базам данных упираются в физические ограничения серверов. Для работы с графом связей из миллиардов пользователей и мгновенной доставки контента инженеры разработали ряд специфических распределенных алгоритмов.

**1. Instagram Sharded Snowflake**

*Область применения*: генерация первичных ключей для шардированных реляционных баз данных без использования центрального координатора.

При объеме в 40 млрд постов данные распределены по шардам PostgreSQL. Использование стандартного UUID в такой системе делает ключи слишком длинными и усложняет поиск и сортировку. В одном из решений - алгоритме Snowflake от Twitter уменьшили размер идентификаторов (с 96+ до 64 битов) и сделали сортировку по времени. Но у них осталась проблема - если клиент запрашивает пост по ID, API-шлюзу нужна центральная таблица маршрутизации, чтобы понять, на каком сервере лежит этот пост. При крайне больших RPS эта таблица становится точкой отказа. И инженеры Instagram модифицировали алгоритм Snowflake, вшив логику маршрутизации прямо в сам ключ. Состав 64-битного bigint ID:<br>• 41 бит: Timestamp в миллисекундах.<br>• 13 бит: Logical Shard ID (до 8192 шардов).<br>• 10 бит: Локальный Auto-increment счетчик (для генерации уникальных ID). Как видно *ключевое* отличие в том, что в ключе навсегда зашит номер шарда, на котором хранятся данные. Когда API-шлюз получает запрос GET, он применяет побитовую маску к ID в нём, моментально извлекает номер шарда и направляет соединение прямо в нужную базу данных.

*Источник*: [Sharding & IDs at Instagram](https://instagram-engineering.com/sharding-ids-at-instagram-1cf5a71e5a5c).

**2. Facebook Haystack**

*Область применения*: хранение миллиардов мелких медиафайлов на жестких дисках.

В масштабах Instagram и Facebook хранение медиаконтента упирается не в объем жестких дисков, а в количество операций ввода-вывода в секунду. Исторически Facebook хранил фотографии на NAS-серверах с файловыми системами семейства ext (POSIX). В таких системах для каждого файла создается структура метаданных - inode. Чтобы прочитать файл, операционная система должна сначала прочитать директорию, затем загрузить inode с диска, и только потом прочитать сами блоки данных. При миллиардах небольших фотографий общий объем inode превышает доступную оперативную память серверов и ОС вынуждена сбрасывать кэш метаданных и постоянно обращаться к жесткому диску, чтобы найти файл. Инженеры Meta отказались от хранения фото как отдельных файлов - они создали специализированное объектное хранилище. ЕГо дисковое пространство серверов разбивается на гигантские файлы по 100 ГБ (Физические тома). Сами фотографии в данном алгоритме это т.н. "иголки". При загрузке фотографии она не создает новый файл, а дописывается в конец этого 100-гигабайтного тома. Главная инновация Haystack заключается в полном отказе от дисковых метаданных (inode) в пользу компактного in-memory индекса. Когда сервер стартует, он считывает 100-гигабайтныe тома и строит в оперативной памяти хэш-таблицу. Для каждой фотографии хранится всего 4 параметра: Key (ID фотографии, 64-bit), Alternate Key (размер миниатюры, 32-bit), Offset (смещение в байтах от начала 100-гигабайтного файла, 64-bit) и Size (размер фото в байтах, 32-bit). Система получает запрос GET /photo/12345. По итогу в данном алгоритме сервер смотрит в оперативную память (O(1)), находит смещение и делает ровно один системный вызов pread(). Головка диска лишь один раз переходит в нужную позицию и считывает Size байт, что значительно увеличивает пропускную способность жесткого диска (по сравнении с трему операциями изначально).

**3. Two-Pass Feed Ranking**

Вместо того чтобы анализировать сами посты, Instagram анализирует графы поведения пользователей с помощью алгоритма векторных представлений. Инженеры взяли алгоритм анализа текстов (где слова, часто стоящие рядом, имеют похожий смысл) и применили его к аккаунтам.
Если миллионы людей лайкают аккаунты с похожим контентом или иным контентом в рамках одной сессии, алгоритм ig2vec помещает эти аккаунты очень близко друг к другу в 64-мерном векторном пространстве. Когда вы открываете Explore, система мгновенно смотрит в Redis и берет  10-20 аккаунтов, которые вы лайкали или сохраняли за последние дни.

| **Apache Kafka** | Брокер сообщений | Асинхронная очередь (брокер). Выступает "предохранителем" системы: вечером, когда нагрузка возрастает многократно, Kafka накапливает миллионы лайков и комментариев и плавно передает их в базы данных контролируемыми пачками (Batching), не давая базам "упасть". |
| **Haystack** | Объектное хранилище фото и видео | Самописная замена классическим дискам. Отказывается от стандартных файловых систем (POSIX), собирая миллионы мелких фотографий в огромные физические тома по 100 ГБ. Индекс файла держится в ОЗУ, что позволяет считывать фото за одно касание диска (O(1)), решая проблему узкого места ввода-вывода (I/O). |
| **APNs (Apple) / FCM (Google)** | Шлюзы Push-уведомлений | Собственные серверы не могут напрямую вернуть свернутое приложение. Бэкенд Instagram формирует уведомления (например, о новом сообщении в Direct) и пачками по gRPC отправляет их в инфраструктуру Apple и Google, которые уже доставляют push на миллионы конкретных устройств. |
| **RabbitMQ / Celery** | Распределенные очереди задач  В отличие от Kafka (которая работает как шина потоковых данных), очереди задач нужны для тяжелых единичных процессов. Например, когда пользователь загружает видео, фоновые воркеры забирают задачу, транскодируют видео в разные разрешения (1080p, 720p) и форматы (H.264, VP9) асинхронно, не блокируя API-сервер. |

## 9. **Обеспечение надёжности**

### 9.1. Надежность инфраструктуры

| Технология | Метод обеспечения надёжности |
| :--- | :--- |
| **BGP Anycast + Geo-DNS** | **Маршрутизация на уровне провайдеров.** Если целый дата-центр уходит в оффлайн, BGP-маршрутизаторы провайдеров автоматически перестраивают маршруты на следующий живой дата-центр. |
| **L4 Balancer** | **ECMP + Active-Active + DSR.**<br>• *ECMP (Equal-Cost Multi-Path):* Маршрутизация трафика по нескольким лучшим путям одновременно, распределяя пакеты между всеми серверами балансировки поровну.<br>• *Active-Active:* Все балансировщики работают одновременно. При отказе одного, трафик мягко перестраивается на соседей.<br>• *DSR (Direct Server Return):* Ответы от серверов идут клиенту напрямую, минуя балансировщик, что на защищает L4 от перегрузки исходящим трафиком сети. |
| **L7 Proxy** | **Горизонтальное масштабирование + Circuit Breaker.**<br>• *Горизонтальное масштабирование:* Кластер прокси-серверов расширяется добавлением новых машин при пиках трафика.<br>• *Circuit Breaker:* Паттерн, отслеживающий ошибки микросервисов. Если микросервис лайков начинает возвращать 500-е ошибки, L7-прокси временно перестает слать туда запросы, чтобы сервис мог восстановиться, не допуская каскадного отказа всей сети. |
| **PostgreSQL** | **Master-Replica + Patroni + WAL-логи.**<br>• *Patroni:* Если Master-сервер падает, Patroni замечает это и автоматически назначает одну из реплик новым мастером за несколько секунд.<br>• *WAL (Write-Ahead Logging):* Каждое изменение в базе сначала пишется в непрерывный лог. |
| **Cassandra** | **P2P Архитектура + Replication Factor.**<br>• *Peer-to-Peer:* В Кассандре нет понятия "Master" или "Slave". Все узлы равны. Это физически исключает единую точку отказа.<br>• *RF=3 (Фактор репликации):* Каждая строчка (сообщение или лайк) физически копируется на 3 разных сервера, стоящих в разных серверных стойках. Если сгорает целая стойка, кластер продолжает работу, так как у него остаются 2 живые копии. |
| **Redis** | *Failover:* У каждого мастер-слота есть своя реплика. Если мастер выходит из строя, кластер автоматически голосует и "повышает" реплику до мастера, сохраняя доступность кэша. |
| **Graph DB** | **Глобальная гео-репликация.**<br>• Главный узел находится в США и координирует записи. Кэширующие узлы разбросаны по разным странам. Это позволяет отдавать граф связей пользователю за кратчайшее время. |
| **S3** | **Избыточное кодирование.** Файл разбивается на части, к которым добавляются блоки четности. Это позволяет потерять до половины физических серверов хранения без потери байта данных, занимая при этом меньше места на диске, чем классическое 3-кратное копирование. |
| **Apache Kafka** | *Offsets:* Встроенная система курсоров. Если фоновый Worker, обрабатывающий подписки, сломается, то после перезапуска он спросит у Кафки свой Offset и продолжит читать очередь ровно с того события, на котором сломался. Ни одно действие пользователя не потеряется. |

### 9.2. Асинхронные паттерны

Разделение синхронного ответа и физической записи в базу — главный паттерн выживания системы под сверхнагрузками.

*   **Изоляция записи:** Тяжелые операции (простановка лайков, отправка сообщений, обновление подписок) не пишутся в БД напрямую. `Interaction Service` или `Subscription Service` отправляют события в **Kafka** и сразу отдают пользователю `200 OK`. Если Cassandra или PostgreSQL временно перегружены или недоступны, пользователи этого не заметят. Данные накопятся в Kafka и запишутся консьюмерами после восстановления БД.
*   **Защита от Thundering Herd:** При публикации популярного поста миллионы запросов к пустой базе данных могут её поломать. Redis использует паттерн **Lease-блокировок**: при кэш-промахе только один поток идет в PostgreSQL, остальные ждут миллисекунды и получают готовый ответ из кэша.

### 9.3. Graceful Degradation

Система спроектирована с учетом частичных отказов. Если падает один некритичный сервис, приложение продолжает работать для конечного пользователя, скрывая сломанные элементы интерфейса.

*   **При отказе `Content Service`:** Загрузка новых фото/видео становится недоступна. Однако `API Gateway` отдает пользователю старую, ранее закэшированную ленту из Redis (Feed Cache), чтобы экран при входе в приложение не был пустым.
*   **При отказе `Like Service` / `Comment Service`:** Пользователи продолжают скроллить ленту новостей и смотреть видео. Кнопки лайков/отправки комментариев временно отключаются, а счетчики показывают устаревшие значения из кэша Redis.
*   **При отказе `Messenger Service`:** Вкладка чатов показывает статус "Подключение...". Пользователь не может отправлять и читать новые личные сообщения, но основной функционал приложения продолжает работать в штатном режиме.
*   **При отказе `Auth Service`:** Регистрация и вход с новых устройств падают. Однако уже авторизованные пользователи (у которых `access_token` валиден и лежит в `sessions` Redis) продолжают полноценно пользоваться приложением без прерываний.
*   **При отказе `Relationship Service`:** Кнопка "Подписаться" возвращает ошибку, но пользователи продолжают смотреть ленту тех, на кого подписались ранее, так как эти связи уже закэшированы и собраны Fan-out воркером.
*   **При отказе `Search Service`:** Отключается панель автодополнения и поиска по хэштегам. Вкладка "Explore" переходит в резервный режим и отдает предсобранный статический список "Глобальные тренды" вместо персональных рекомендаций.
*   **При отказе `DWH`:** Для рядовых пользователей не меняется ничего. Статистика временно перестает обновляться. Данные аналитики копятся в буфере Apache Kafka и будут залиты в ClickHouse батчами сразу после его восстановления.
*   **При отказе `Feed Service`:** Если система сборки новых лент сломалась, `API Gateway` отдает пользователю старую, ранее закэшированную ленту из Redis, чтобы экран не был пустым.

### 9.4. Graceful Shutdown

При обновлениях сервисы завершают работу без потери данных пользователей:
1. Оркестратор отправляет контейнеру сигнал `SIGTERM`.
2. L7-балансировщик исключает этот под из ротации и перестает слать туда новые HTTP-запросы.
3. Фоновые консьюмеры перестают брать новые задачи из Kafka.
4. Микросервис ждет (до 30-60 секунд) завершения обработки текущих запросов и сброса данных в БД.
5. Фиксируется актуальный `offset` в Kafka, после чего процесс безопасно завершается.

### 9.5. Мониторинг

*   **Метрики:** **Prometheus** автономно собирает телеметрию (CPU, RAM, RPS, размер очередей Kafka) со всех микросервисов. Независимость Prometheus гарантирует, что мониторинг работает даже при отказе бизнес-сети.
*   **Алертинг:** При аномалиях (например, рост 500-х ошибок на `Auth Service` > 2%) Alertmanager автоматически вызывает инженеров.
*   **Трассировка:** К каждому API-запросу на Gateway прикрепляется `Trace-ID`. Это позволяет проследить весь путь сложного запроса через L7, микросервисы, Kafka и базы данных, чтобы мгновенно находить "узкое горлышко" при деградации ответа.

Детальный расчет ресурсов произведен для хаба **Singapore (APAC)**, который обслуживает 42% мирового трафика. Глобальный пиковый RPS системы составляет **~795 500 RPS** (сумма из таблицы п. 3.3).

### 11.2 Расчет баз данных и хранилищ

Опираясь на предыдущие расчеты, общий объем медиа составляет **3.89 Эксабайт (3 983 Петабайт)**, а реляционные базы данных и индексы — **~66.4 Петабайт**. 
Рассчёт для Сингапура:

1. **S3 / Haystack:** 
   * Доля Сингапура: `3.89 ЭБ × 0.42 = 1.63 Эксабайта (1 630 000 ТБ)`.
   * Сервер хранения (Storage Node): 36 жестких дисков по 18 ТБ = ~648 ТБ.
   * *Требуется серверов:* 1 630 000 / 648 ≈ **2 515 серверов**.
2. **Cassandra:** 
   * Приходится ~90% объема БД (~60 ПБ глобально). Доля Сингапура: 25 ПБ.
   * Учитывая Replication Factor = 3: 75 ПБ.
   * Сервер БД: 4x 7.6TB NVMe = ~30 ТБ.
   * *Требуется серверов:* 75 000 ТБ / 30 ТБ = **2 500 серверов**.
3. **PostgreSQL:** 
   * Глобальный объем ~6 ПБ. Доля Сингапура: 2.5 ПБ. С репликацией (x3): 7.5 ПБ.
   * Сервер БД: 4x 7.6TB NVMe = ~30 ТБ.
   * *Требуется серверов:* **250 серверов**.
4. **L4 / Network Edge:**
   * Глобальный пиковый трафик оценивается в ~43 Тбит/с. Доля Сингапура: ~18 Тбит/с.
   * Один сервер с сетевой картой 100GbE реально маршрутизирует ~80 Гбит/с.
   * *Требуется серверов:* 18 000 / 80 = **225 серверов**.
